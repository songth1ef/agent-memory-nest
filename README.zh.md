# agent-memory-nest

[English](README.md) | **中文**

> **所有 agent，共用一个大脑。**
> 一个 git 仓库，装下你所有 AI agent 的规则、记忆和上下文：不分机器，不分厂商。

## 为什么需要它

如今每个编码 agent 都有自己的记忆，但都只留给自己：

- **绑在一台机器上。** Claude Code、Codex、Gemini CLI、Kimi Code、Antigravity、Hermes、OpenClaw 的记忆都存在本地，换一台电脑就从零开始。
- **绑在一个厂商上。** Claude 学到的东西只属于 Claude，换成 Codex 又得从头讲一遍。
- **绑在一个账号上。** 订阅到期、账号被封或工具停服，**你几个月积累的记忆会一夜清零，而且找不回来。**

agent-memory-nest 把这些记忆搬进一个归你所有的 git 仓库。每个 agent 都从同一个巢里读取、往同一个巢里写回，所以它们共用同一个大脑。是一个蜂巢意识，而不是一群互不相识的陌生人。

## 为什么值得长期记

**给 agent 写记忆，是用 AI 干活时复利最高的习惯。** 每一次纠正、每一条约定、每一个踩过的坑，记下来就不用再讲第二遍。agent 记得越多，越懂你的习惯和项目，用起来越顺手，你花在反复纠正同样错误上的时间就越少。而且这些积累属于你，不会随某个工具、某个账号或某份工作消失。

**适合谁：** 所有用 AI agent 干活的人。前提只有 git，加一个 Claude Code、Codex 这样的命令行 agent。

## 有什么不同

- **极易上手，不用服务器。** 只要一个私有 git 仓库：不部署、不常驻进程、不开端口。装好之后照常用你的 agent，不用学任何新东西。git 是唯一的同步通道，在 NAT 后面或离线的机器，重新联网后照样能同步。
- **不只是记忆。** 巢里还放着规则和方向，冲突时按固定的优先级裁决，所以一群 agent 遵循的是同一套指引，而不只是共享笔记。
- **写入边界清楚。** 每个 agent 只写自己的目录。共享记忆只能经过一次有人审核的蒸馏来修改。
- **按任务加载。** 会话开始时只加载一层很小的常驻内容，其余按需读取，所以记忆越来越多，上下文也不会膨胀。
- **天生私密。** 巢本来就应该放在私有仓库里，还可以用 git-crypt 全程加密：**加密后，哪怕是 GitHub 的工作人员也读不到你的记忆内容。**

## 快速开始

1. **用这个模板建一个私有巢。** 在 GitHub 上点 **Use this template**，选 **Private**；或者运行：

   ```bash
   gh repo create my-nest --private --template songth1ef/agent-memory-nest
   ```

2. **在你用的每台机器上 clone：**

   ```bash
   git clone git@github.com:<你的账号>/my-nest.git ~/agent-memory-nest
   ```

3. **给每个 agent 工具安装**（Windows 用对应的 `.ps1`）：

   ```bash
   bash ~/agent-memory-nest/scripts/install/claude.sh
   ```

4. **开一个新会话。** 有启动 hook 的工具会打印 `agent-nest context bundle`；任何工具都可以问 agent 一句「巢里关于我写了什么？」，确认它读到了规则。

可选：把 `config.example.md` 复制成 `config.md`，调整拆分阈值、蒸馏提醒等设置。在 `queen/agent-rules.md` 写你的规则，在 `queen/strategy.md` 写你的目标。

## 怎么用

装好之后，你照原来的方式干活就行：

- **agent 边干边记。** 定下一个决策、学到一个教训、项目往前推了一步，agent 会把它写下来：有时是它自己判断该记，有时是你说一句「记一下」。
- **同步不用你管。** 拉取、提交、推送全由 hook 完成，你不用为记忆碰 git。
- **换机器、换工具，上下文不变。** 在笔记本、云服务器上开新会话，或者换一个 agent，都从同一个巢接着干。

典型的一周：

- **在办公室**，一个 agent 记下项目进展和你们约定的工作规则。
- **回到家**，新会话直接接着这些上下文干，不用从头交代。
- **在云服务器上**，另一个 agent 接手同样的项目状态和决策。

## 工作原理

```
   Claude Code     Codex     Gemini CLI     Kimi Code     ...
        │            │            │             │
        └────────────┴─────┬──────┴─────────────┘
                           │  会话开始时 pull
                           │  每次写入后 commit + push
                           ▼
                 ┌────────────────────┐
                 │  你的私有巢        │   规则 · 记忆 · 上下文
                 │  （一个 git 仓库） │
                 └────────────────────┘
```

**优先级链。** 两个来源冲突时，以优先级高的为准，绝不合并。

```
规则 > 战略 > 共享记忆 > agent 记忆 > 项目笔记 > 工作流笔记
```

**会话生命周期。**

1. **开始。** 会话启动 hook 拉取巢，只加载一层很小的常驻内容：核心规则，加上当前目标和近期动态的简短摘要。
2. **工作。** 每次写记忆前，hook 再拉取一次；写完后提交并推送。写入冲突的窗口从「整场会话」缩小到「单次写入」。
3. **结束。** 停止 hook 做最后一次提交和推送，作为兜底；没有改动就什么都不做。

没有 hook 的工具，按启动指令文件走同样的步骤，在会话结束时同步。

**几乎零维护。** agent 边干活边写记忆，同步全由 hook 完成。唯一需要手动的是**蒸馏**：把各个 agent 学到的东西整理合并进共享记忆，写入前经过一次审核。**每月一次**就够了。

## 只加载任务需要的

记忆会越来越多，但一次会话不该把它们全读一遍。以下是作者自己的巢的实测（2026 年 11 月，token 为估算值）：

| 一次会话加载什么 | 文件数 | 大小 | Token |
|---|---|---|---|
| 旧方式全量加载：规则、战略、全部共享和 agent 记忆 | 37 | 254 KB | 约 79,000 |
| **只加载常驻层，默认的启动方式** | 4 | 5 KB | **约 1,600** |
| 常驻层，加上任务需要的那个主题 | 6 | 18 KB | 约 5,400 |
| 巢里的全部记忆文件 | 283 | 1.6 MB | 约 480,000 |

默认启动只读全量加载的约 **1/50**，而整个巢已经放不进大多数模型的上下文窗口。所以历史记忆是在任务需要时检索，而不是一开始就全部加载。

## 不只是共享笔记

- **把已有的记忆带过来。** Claude Code、Codex、Kimi Code 原本存在单台机器上的记忆，可以蒸馏进巢里。换了新机器、账号被封或工具停服，都不用从头再来。
- **agent 之间能互相留言。** 基于 git 的信箱，让一个 agent 给另一个 agent 留任务或留言，同一台机器、不同机器都行，不需要额外服务。
- **升级永远不碰你的数据。** 你的巢是一个公开模板的私有副本。协议更新只替换协议文件，不会动你的规则、记忆和项目。
- **协议有版本号。** 协议使用 `主版本.次版本` 编号：次版本保证向后兼容，只有主版本升级才需要你迁移。

## 真实场景

**多台机器，同一个项目。** 你在台式机上开始一个功能，晚上在笔记本上接着写，再让云服务器上的 agent 通宵跑完整测试。每一处读到的都是同样的项目状态和决策，干完的事也都写回巢里。

**换工具。** 某个任务你从 Claude Code 换到 Codex。Codex 一启动就带着你的规则、偏好和项目历史，因为这些存在巢里，不在 Claude 里。

**丢了账号或工具。** 订阅过期、账号被封，或者工具停服了。你的记忆从来不只存在那里，所以下一个装上的 agent 能从上一个停下的地方接着干。

## 经过实战检验

作者从 2026 年 4 月起每天都在用这套方案：**10 台机器**（Windows、macOS、Linux 服务器和一部安卓手机）、**10 种 agent 工具**、**30 多个 agent 实例**，共用一个巢。协议里的规则来自日常使用中真实遇到的问题，而不是一份设计文档。

## 支持的工具

| 工具 | 安装 | 同步方式 |
|---|---|---|
| Claude Code | `scripts/install/claude.sh` | hook：会话开始、每次写入、回合结束（含规则检查） |
| Codex | `scripts/install/codex.sh` | hook：每次写入、回合结束 |
| Kimi Code | `scripts/install/kimi.sh` | hook：会话开始、每次写入、回合结束 |
| Antigravity | `scripts/install/antigravity.sh` | hook：会话开始、回合结束 |
| Gemini CLI | `scripts/install/gemini.sh` | 启动指令；agent 在会话结束时同步 |
| Hermes | `scripts/install/hermes.sh` | 写在 `SOUL.md` 里的启动指令 |
| OpenClaw | `scripts/install/openclaw.sh` | 启动指令 |
| 豆包办公、WorkBuddy | `scripts/install/doubao.sh`、`workbuddy.sh` | 在对话里执行的启动指令 |
| 任何读取 markdown 指令文件的工具 | `scripts/install/generic.sh <名称> <文件>` | 启动指令 |

每个安装脚本都有对应的 PowerShell 版本，`scripts/uninstall/` 里有配套的卸载脚本：只移除它装上的东西，永远不碰你的记忆。

## 目录结构

```
queen/            agent-rules.md、strategy.md        由你来写
shared/           resident.md、memory.md、主题文件    只在蒸馏时修改
agents/<host>/<agent-id>/                            每个 agent 一个目录，只有它自己写
agents/<host>/config.md                              单台机器的设置
projects/         每个项目一份状态笔记
workflow/         换了工作也带得走的方法
decisions/        关于巢本身的决策记录
config.md         整个巢的设置（从 config.example.md 复制）
AGENTS.md         所有 agent 遵守的协议（CLAUDE.md 是它的副本）
scripts/          安装、hook、蒸馏、规则检查、信箱
docs/             信箱、加密、记忆结转、故障排查
```

## 与其他方案对比

| | 工具自带记忆 | 记忆服务器 | 记忆 SDK / 平台 | **agent-memory-nest** |
|---|---|---|---|---|
| 例子 | Claude Code、Codex 的记忆 | ai-memory | mem0、Letta | |
| 你要运行什么 | 不用 | 一个自己部署的服务进程 | 一个库或托管服务 | **只要 git** |
| 跨厂商 | 不支持 | 支持 | 面向你自己开发的应用 | **支持** |
| 跨机器 | 不支持 | 通过你的服务器 | 取决于部署方式 | **通过任意 git 远端** |
| 数据在谁手里 | 工具，且只在一台机器上 | 你 | 你或服务商 | **你，在私有仓库里** |
| 给 agent 的规则和方向 | 各工具各管各的 | 不是重点 | 不是重点 | **内置，带优先级链** |

取舍：记忆服务器在检索、自动捕获和跨工具会话交接上更强。agent-memory-nest 把记忆保持为纯 markdown，由 agent 有意识地读写，除了一个 git 仓库，什么都不要求你准备。

## 常见问题

**多个 agent 同时写会冲突吗？**
很少。每个 agent 只写自己的目录，共享记忆只在蒸馏时修改。每次写入前都会先拉取，所以只有两台机器在同一时刻写同一个文件才会冲突。真遇到时，这次写入会被拦下，由你手动合并。

**能把 API key 存进巢里吗？**
不能，私有仓库也不行。账号被盗或权限配错都会让它泄露。密钥请放在环境变量或专门的密钥管理工具里。

**私密记忆怎么保密？**
把巢放在私有仓库里；如果内容必须连 git 托管方都读不到，就开启 git-crypt。agent 读写的是明文，提交进仓库的是密文。加密防的是托管方和拿到仓库副本的人，防不了运行 agent 的那一方。

**Claude Code 以外的工具能用吗？**
能。Claude Code、Codex、Kimi Code 通过 hook 在每次写入时同步。任何启动时读取 markdown 指令文件的工具，都可以遵循同一套协议，在会话结束时同步。

**公司项目的代码会被收进巢里吗？**
不会。除非你明确让某个项目加入，否则不会吸收任何工作项目的内容；即使加入，内容也要先脱敏、经你审核才会写入。

## 不做什么

- **不做服务器或同步服务。** 所有同步都靠 git push 和 pull。
- **不做权限控制层。** 可见性由 git 托管平台自己的权限管理。
- **不做实时协作。** git 本来就是异步的。
- **不做图形界面。** 一切都通过你的 agent 或 git 命令行完成。
